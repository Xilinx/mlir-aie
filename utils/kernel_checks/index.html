About this dashboard

One page, utils/kernel_checks/index.html, with no build step: the nightly workflows copy it to gh-pages:dashboard/ each time they publish, and it reads the data they publish beside it.

Where the data is

kernel-checks/<npu>/
the kernel checks, per NPU, written by nightlyKernelChecks.yml through publishKernelResults.yml
component-checks/<check>/
the performance, routing and placement checks, per check: sa-placer and sa-placer-hw, written by nightlyComponentChecks.yml; allocator and router, written by modelBasedTests.yml
ci-health/
status.json, the critical test workflows' figures, merge time and the scheduled workflows' recent runs, and history.json, a point a day of those figures; written every six hours by publishCiHealth.yml (utils/kernel_checks/ci_health.py)

Both are written by utils/kernel_checks/publish.py in one format: runs/<id>.json (one run's record), runs.json (a summary per run), latest.json (the newest record that published numbers; the kernel checks' pull-request report compares against it) and history/<metric>.json (every run's value of one metric per case). A kernel NPU also has catalogue.json, every kernel factory and how its cases fared. Runs older than 90 days thin to weekly. Files carry a schema number, and the page sets aside a newer one rather than misread it.

Lower is better, except where a metric says higher is better: rates such as tokens or images per second, and verified counts. A change is colored by whether it is worse, not by its sign, and each chart's axis says which way is better. A change counts once it passes the metric's threshold in utils/kernel_checks/thresholds.json, which the pull-request report reads too; a noisy timing also has to pass a multiple of its run-to-run spread. Runs started by hand are charted but never compared against.

Working on the page

python3 utils/kernel_checks/preview.py --fetch                 # the published data, this page
python3 utils/kernel_checks/preview.py --scenario bad-night      # a synthetic failing night on top
python3 utils/kernel_checks/preview.py --site components --scenario bad-night
python3 -m pytest test/test_kernel_checks_page.py                # the page's code, under node

To add a section: publish its checks to component-checks/<check>/ from a nightly job (add the check to COMPONENTS in publish.py), then add the section to SECTIONS and its checks to BANDS in the page.

    Run times
    How this section works

    publishCiHealth.yml runs every six hours: utils/kernel_checks/ci_health.py asks GitHub's API, with the workflow's own token, for each workflow's recent scheduled runs on main and, for those on the NPU and bench machines, the jobs of the latest run, and writes ci-health/status.json beside this page. The scheduled jobs are judged on their scheduled runs on main alone; the tests that gate a merge on their runs on main, and on how often a pull-request or merge-queue commit needed a re-run to pass.

    Every workflow is listed once, in one of two kinds. Tests that gate a merge are the workflows the merge queue runs, listed under critical in the file below. They also run on main, nightly and for some after each push; each is judged on its latest run there, names the jobs that failed in it, and is late when main has not run it for 36 hours. Main failing 2 of its last 5 runs, the latest passing, is intermittent: amber, worth watching. Its pass rate on main and how often a pull-request or merge-queue commit needed a re-run to pass, over two weeks, are its normal: shown under it, never judged, since a hardware runner that wedges now and then is usual.

    Nightly and scheduled jobs are judged on their latest scheduled run on main, and are late when it started more than one and a half of their periods ago (36 hours for a nightly). A cancelled run has no result: the run before it stands. A job still queued after six hours almost always means no runner with its labels is online: red, since the nightly will not run until a machine is back.

    Run time charts one workflow's finished runs, oldest first: how long each took from its first job's start, and how long its slowest job waited for a runner. A failed or timed-out run's point is red, one that lost its runner or found none amber; hover a point for its commit, click it for the run. A run on main that timed out counts as failed; one whose runner was lost, or never came, is the machines' and counts neither way.

    Merging: the pull requests merged in the last two weeks and how long each was open, drafts included; and those open now.

    To list another workflow, add it to utils/kernel_checks/ci_workflows.json.

      How these checks work

      nightlyKernelChecks.yml runs at 06:00 UTC on an npu1 (AIE2) and an npu2 (AIE2P; Strix or Krackan, which each run names) bench runner, on pull requests that bump the Peano pin, and on demand. Each run checks every case in test/python/npu/kernel_cases.py for correctness (test_kernels_e2e.py -m extensive: every case, every edge-data case, three random seeds), then times the cases that passed with test_kernels_perf.py -m perf, and writes a catalogue of every factory and how its cases fared.

      Only the nightly and an unfiltered dispatch on main publish, and only in the turbo power mode, which the bench runners set at boot: in any other mode the timing step refuses rather than chart numbers taken at another clock. A failed preflight or passthrough sanity check publishes nothing from that NPU; a failing case costs only its own series a point. A run that does not publish gets a report of its failures and of its changes against the last nightly in its job summary (utils/kernel_checks/pr_report.py), kept as a comment on a Peano pull request.

      What each case records

      Cycles are the minimum over the traced calls of a kernel whose contract says Trace.whole_call(); their spread, and whether the trace buffer held every call, are in the row's range. Cycles and object size are the numbers the checks gate on; host time moves with the machine, so it only counts past three times its run-to-run spread, and only against a night on the same part. A dashed line on a chart marks a change of Peano, part, host, runtime, driver, kernel sources or measurement between nights; nothing is compared across a change of measurement.

      The views

      Summary: a verdict per NPU against the nightly before, whose date it names; what needs a look (failures, the cases that got slower or bigger last night, and any of the timing harness's own tests that failed); and every case whose cycles or object size moved past its threshold since the nightly before, as the two numbers and their dates. Its Window switch compares each case's first and latest nightly of the last 30 instead. All kernels: a line per kernel with, per NPU, its state last night, its cases' cycles now, and how many got slower or faster over the last 30 nightlies, since the first night one of them moved; those that need a look first. A kernel's own page (#view=kernel&kernel=<factory>) charts each of its cases' actual cycles (or size, or host time) night by night, and tables each case's cycles now and then.

      How to run the same checks locally, and to measure a kernel change against the code before it, is in the kernel library's testing section.

      Performance

      MobileNet, Llama 3.2 1B and YOLO26n, compiled, run and verified nightly on an npu2.

      Actions runs MobileNet design Llama design YOLO26n design
      How these checks work

      utils/component_checks/sa_placer_hw.py runs in nightlyComponentChecks.yml at 06:30 UTC on an npu2 bench runner (Strix or Krackan; each run names its part). The MobileNet design is placed with the SA placer at seeds 3 (the design's default), 2 and 7, then compiled once per seed and effort and run and verified at every power of two from 1 to 64 images per launch, every image checked. A publishing run refuses to time unless the NPU is in turbo mode.

      utils/component_checks/llama_chain_hw.py runs in the same workflow, queued on the same NPU. The Llama 3.2 1B 16-layer persistent decode is compiled twice in one fresh cache, cold then warm, its 4 tokens per dispatch checked one by one against the numpy oracle, then timed.

      utils/component_checks/yolo26n_hw.py runs after it, on the same NPU. The YOLO26n 640×640 detector is compiled twice in one fresh cache, cold then warm, run on 8 COCO128 images, each checked against the numpy oracle and, for information, onnxruntime, then timed at batch 1 and checked and timed again at batch 8.

      What each run records

      Dispatch and end-to-end per image are the fastest of 20 launches, over the images in the launch. Records from before one dispatch-time compile served every batch (each batch compiled on its own) are not charted beside them.

      To compile one seed at one effort and run every batch as the nightly does, from programming_examples/ml, with E 0.05 for the design's default effort or 1.0 for full effort:

      python -m mobilenet.aie2_mobilenet_iron --sa-seed N --sa-effort E --dynamic 1 2 4 8 16 32 64 -w 20 -i 20

      and every seed and batch, as the nightly does:

      python utils/component_checks/sa_placer_hw.py --out perf.json --meta meta.json

      The Llama decode, from programming_examples/ml/llama_3_2_1b after gen_llama_data.py has built data/ from the model's weights:

      python aie2_decode.py --p-max=4 --kset=8 --n-layers=16 --t=128 --full-elf-path build/chain_persist_grow_N16_PT4.elf && python test_decode.py --p-max=4 --kset=8 --n-layers=16 --t=128 --elf build/chain_persist_grow_N16_PT4.elf

      and as the nightly does:

      python utils/component_checks/llama_chain_hw.py --out perf.json --meta meta.json

      The YOLO26n detector, from programming_examples/ml/yolo26n after gen_yolo_data.py has built data/ from the quantized model:

      python yolo26n.py --images $IRON_EXAMPLE_WEIGHTS_DIR/yolo26n/coco128/images/train2017 --n 8

      and as the nightly does:

      python utils/component_checks/yolo26n_hw.py --out perf.json --meta meta.json

      Routing

      The packet router against its model, on CPU with no NPU: does every design still route legally, and how long are its routes.

      Actions runs Router source
      How these checks work

      modelBasedTests.yml runs at 03:17 UTC from main and on demand, on a hosted runner with an assertions build. Each night takes a new range of seeds, so the router meets designs it has not seen; the range is in the run's record, and a failure names the seeds to run again. The nightly and an unfiltered dispatch on main publish, and a check that fails still publishes what it measured.

      router_properties.py generates designs whose routing the model can construct or rule out, on npu1, npu2 and xcvc1902, routes each with hops on and off, and verifies the result: legal, deterministic, as short as the constructed routing, warned and rejected as the model predicts. Per device it records the properties that failed, the routings that failed or were illegal, the hops over the constructed routing, the arbiter msels per design and the time per design.

      router_mutation.py changes routed designs in ways with a known answer (the router must route it, reject it, or route it the same), and corrupts routed output to measure how often the model's verifier notices. It records the cases that failed and the corruptions the verifier missed.

      python test/create-packet-flows/nightly/router_properties.py --device npu2 --seeds 2000 --first-seed N
python utils/router_testing/router_mutation.py --device npu2 [--hops-off] --seeds 400 --first-seed N

      Placement

      The SA tile placer and the buffer allocator: does every design still place, and how tight are the placements. The seed sweep and the allocator run on CPU; MobileNet's placements run on an npu2.

      Placer runs Placer source Allocator runs Allocator source
      How these checks work

      nightlyComponentChecks.yml runs at 06:30 UTC from main, on pull requests that touch the placer or these checks (the seed sweep only), and on demand. The nightly and an unfiltered dispatch on main publish; a check that fails still publishes what it measured, and its record lists the failed seeds and runs.

      Seed sweep (no hardware)

      utils/component_checks/sa_placer.py, on a hosted runner: aie-opt places two fixtures, the 4-core design in test/place-tiles/sa_placer/test_sa_effort.mlir and MobileNet before placement (utils/component_checks/fixtures/mobilenet.mlir), with seeds 1 to 20 at full effort. Per fixture it records how many seeds failed to place, the SA placer's final cost (mean and worst), and the CPU time and peak memory of a placement.

      aie-opt '--aie-place-tiles=placer=sa_placer sa-seed=N sa-effort=1.0' \
    --mlir-pass-statistics utils/component_checks/fixtures/mobilenet.mlir

      MobileNet placements on hardware (npu2)

      utils/component_checks/sa_placer_hw.py: MobileNet is placed with seeds 3 (the design's default), 2 and 7, then compiled once per seed and effort and run and verified at every power of two from 1 to 64 images per launch, every image checked. For each seed it records the placement aiecc chose (a digest of the placed tiles) and its SA cost, replayed with aie-opt. What the placed design then costs to run is under Performance.

      To rerun a whole check, run its script with --out perf.json --meta meta.json (the sweep also needs --aie-opt "$(which aie-opt)"; the hardware check takes --seeds and --batches). It prints a table with a row per seed, or per seed and batch.

      Buffer allocator model-based tests (no hardware)

      allocator_properties.py, from modelBasedTests.yml at 03:17 UTC on a hosted runner: aie-opt --aie-assign-buffer-addresses places 5,000 generated designs and 200,000 with per-bank reservations, each built around a layout known to fit, so a design that does not place is a bug. check-aie runs the same test over the first 200 and 12,000. It records the properties that failed, the designs left unplaced or placed illegally, the bank crossings a better placement avoids, the bank pairs cores share, and the run's wall time.

      python test/assign-buffer-addresses/allocator_properties.py --seeds 5000 --bankres-seeds 200000

      How to choose the placer and a seed for your own design is in section 1 of the programming guide.
